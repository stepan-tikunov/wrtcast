# Title API

Сборка и запуск:

```sh
make
./title-api
```

По умолчанию gRPC-сервер слушает `:50051`, а HTTP/JSON-шлюз — `:8080`.
Настройки:

- `GRPC_ADDR` — адрес gRPC-сервера;
- `HTTP_ADDR` — адрес HTTP-шлюза;
- `MOVIE_PROVIDER_BASE_URL` — базовый URL провайдера (если не задан,
  используется встроенный);
- `MOVIE_PROVIDER_USER_AGENT` — User-Agent ресивера (см. ниже);
- `TITLE_API_PUBLIC_URL` — публичный HTTP-адрес сервиса, используемый в
  ссылках на синтетические HLS master-плейлисты (по умолчанию
  `http://localhost:50052`);
- `TITLE_API_STATE_DB` — путь к SQLite-базе состояния (по умолчанию
  `title-api-state.db` в текущем каталоге);
- `HTTPS_PROXY` / `HTTP_PROXY` — прокси для исходящих запросов, в том числе
  `socks5://…`.

Антибот-сессия создаётся до запуска gRPC-сервера, обновляется каждые пять
минут и сразу же, если запрос наткнулся на новую проверку. После редиректа
провайдера сервис запоминает фактический хост в SQLite и использует его при
следующем запуске; исходный `MOVIE_PROVIDER_BASE_URL` остаётся резервным.

## Docker

Образ для amd64 и arm64 собирается GitHub Actions при каждом изменении
`title-api/` в `master` и публикуется в GitHub Container Registry:

```sh
docker run -p 8080:8080 ghcr.io/stepan-tikunov/wrtcast/title-api
```

Чтобы актуальный хост переживал пересоздание контейнера, подключите volume:

```sh
docker run -p 8080:8080 \
  -e TITLE_API_STATE_DB=/var/lib/title-api/state.db \
  -v title-api-state:/var/lib/title-api \
  ghcr.io/stepan-tikunov/wrtcast/title-api
```

Теги: `latest` (последний `master`), `sha-<коммит>` и `<версия>` для тегов
`v*`. Собрать локально: `docker build -t title-api .`

[`compose.yaml`](compose.yaml) рассчитан на VPS, где сервис доступен только
через WireGuard: HTTP-шлюз слушает WireGuard-адрес сервера, gRPC — только
loopback, наружу ничего не публикуется. Исходящие запросы можно направить
через SOCKS5-прокси на домашнем роутере, чтобы провайдер и его CDN видели тот
же IP, с которого потом загружаются сегменты:

```sh
WG_ADDR=10.0.0.1 EGRESS_PROXY=socks5://10.0.0.2:1080 docker compose up -d
docker compose pull && docker compose up -d     # обновление
```

## Идентификаторы

`title_id` — первые восемь шестнадцатеричных символов SHA-1 от имени хоста
из `MOVIE_PROVIDER_BASE_URL`, за которыми идёт десятичный ID тайтла на сайте.
Автоматически найденный актуальный хост этот префикс не меняет, поэтому ранее
сохранённые ID остаются рабочими. Для провайдера по умолчанию и ID `42185`
получается:

```text
67c18f3642185
```

## Поиск

Полнотекстовый поиск принимает запросы от трёх символов:

```sh
grpcurl -plaintext \
  -d '{"query":"Дюна"}' \
  localhost:50051 \
  title.v1.TitleService/SearchTitles
```

Тот же метод доступен через аннотацию `google.api.http`:

```sh
curl --get --data-urlencode 'query=Дюна' \
  'http://localhost:8080/v1/search'
```

Результаты содержат ID тайтла, название, год и абсолютный URL постера.
Возвращается до 30 результатов с первой страницы поиска провайдера.

## Подробности о тайтле

Полная информация о тайтле, включая достоверный тип (фильм или сериал) и
каталог сезонов и серий, доступна через `GetTitleDetails`:

```sh
curl 'http://localhost:8080/v1/titles/67c18f3643222'

grpcurl -plaintext \
  -d '{"title_id":"67c18f3643222"}' \
  localhost:50051 \
  title.v1.TitleService/GetTitleDetails
```

Для фильмов `durationSeconds` берётся из метаданных плеера, если они есть.
Если нет, сервис открывает подписанный master-плейлист HLS и суммирует
длительности `#EXTINF` выбранного медиаплейлиста. У сериалов длительность
указывается для каждой серии, а не для тайтла целиком.

## Потоки

`GetPlaybackStreams` возвращает потоки фильма, если передан только `title_id`.
Для сериала передайте `season_number` и `episode_number`, чтобы выбрать серию:

```sh
curl 'http://localhost:8080/v1/titles/67c18f3642185/playback-streams'

curl --get \
  --data-urlencode 'season_number=1' \
  --data-urlencode 'episode_number=1' \
  'http://localhost:8080/v1/titles/67c18f3654016/playback-streams'

grpcurl -plaintext \
  -d '{"title_id":"67c18f3654016","season_number":1,"episode_number":"1"}' \
  localhost:50051 \
  title.v1.TitleService/GetPlaybackStreams
```

Для фильмов поля сезона и серии игнорируются.

Ответ содержит по одной записи на каждый доступный плеер. В каждой записи —
человекочитаемое имя, подписанный URL master-плейлиста HLS, список
аудиодорожек без дублей и
доступные субтитры. Видеоварианты намеренно не перечисляются: HLS-плеер
выбирает их сам из master-плейлиста.

У дополнительного плеера перевод и качество опубликованы отдельными
плейлистами. Сервис возвращает каждый перевод отдельным `MediaStream`, но
адаптивный master со всеми качествами собирает только при первом запросе его
URL. Так запуск стоит запросов к CDN лишь для выбранного перевода. Качества
запрашиваются по одному, как у самого плеера, и первый `403` останавливает
остальные. Если CDN отклонил ссылки (`403`, `X-VD: token_decrypt`), сервис
дважды заново запрашивает их у плеера (с вызовом из заголовка `Borth`
прошлого ответа, а если плеер его не принял, со свежей копией страницы), а
если не помогло, отдаёт `502`. Если CDN заблокировал самого клиента
(`X-VD: client_blocked` или `session_blocked`), повторов нет и master
отвечает `403`. Собранный master хранится в памяти шесть часов
(до 4096 последних). Имя перевода записывается в единственную
`audioTracks[].name`. Обязательные для внешнего медиапрокси HTTP-заголовки
возвращаются в `proxyHeaders` как список пар `name/value`. Его CDN ждёт на
каждом запросе, от master до сегментов, те же заголовки, что шлёт плеер:
`Origin` и `Referer` страницы плеера, отпечаток устройства в
`Accepts-Controls` и `Authorizations: Bearer <константа плеера>`. Отпечаток
создаётся один раз и хранится в базе состояния; тот же уходит в `Borth`
запроса воспроизведения, а к ссылкам субтитров, как и плеер, сервис
дописывает `?t=…&b=<отпечаток>`. Chromecast не может выставить такие
заголовки при прямой загрузке URL, поэтому эти потоки нужно передавать через
медиапрокси, который добавляет их и переписывает ссылки дочерних плейлистов и
сегментов.

Если ответ плеера на запрос воспроизведения называет WebSocket (`pnr`,
`pnk`), сервис, как и плеер, держит его, пока источник играет: с первым
запросом master открывает сокет и шлёт `playback_start`, `resumed`, затем
`playing` каждые 30 секунд, `paused` на паузе (сердцебиение до `resumed`
молчит) и `seeked` после перемотки. При переподключении — снова
`playback_start`, а сердцебиение, как у плеера, молчит до следующего
`resumed`. Обрыв, переподключение и отказ после 30 попыток сокет, как плеер,
сообщает в `/stats` сайта плеера. Сервер отвечает `config_update` с
`edge_hash`, и он заменяет отпечаток в `Accepts-Controls`. Поэтому
медиапрокси берёт заголовки не из `proxyHeaders`, а у сервиса:

```sh
curl 'http://localhost:8080/v1/media/<id>/headers?q=720&t=125&p=0&d=2640&b=48000000&e=9000000'
# {"headers":[{"name":"Origin","value":"…"},…],"ttl":20}
```

`q` — играемое качество (цифры метки), `t` — позиция в секундах, `p` — `1`
на паузе, `d` — длительность, которую сообщил ТВ, `b` — байты сегментов этого
`id`, загруженные с начала воспроизведения, `e` — скорость их загрузки в
бит/с; все необязательны, смена `q` отправляет `playback_start`. Заголовки
можно держать `ttl` секунд: 20, пока идёт просмотр (см. ниже), 5, пока не
пришёл первый `edge_hash`. Каждый запрос продлевает сокет и просмотр; без
запросов три минуты они закрываются, а следующий запрос открывает их снова.
Ещё не собранный master при этом собирается, как при запросе master;
неизвестный `id` — `404`. Для источников без сокета ответ — те же постоянные
заголовки. Конец воспроизведения — `DELETE /v1/media/<id>/session` (`204`;
для клиентов, умеющих только GET и POST, — `POST
/v1/media/<id>/session/end`): сокет получает `ended` и закрывается.

Кроме сокета плеер сообщает о каждом просмотре сайту, с которого загружен
(те же cookie, `Origin` и `Referer` страницы, тот же прокси), и сервис делает
это за роутер — для каждого файла страницы, общим для его переводов (для
плеера это смена озвучки). `POST /stat` (форма jQuery) регистрирует просмотр
при первом запуске и повторяется, когда позиция, округлённая до процента,
равна 0, 10, 30, 60 или 97. `POST /events` (форма с JSON) получает события
плеера пачкой раз в 30 секунд от его старта, сразу после первого кадра и
перед сменой качества или озвучки: пустой преролл, `view_start`, `startup`,
`play`, `playback_ready`, `first_frame`, `file_load_complete`,
`heartbeat` каждые 10 секунд, пока идёт воспроизведение (с позицией и
загруженными байтами, между запросами роутера досчитанными), паузы,
перемотки, смены, `view_percent` и конец. Первый запрос заголовков —
нажатие «плей», первый с длительностью — первый кадр. Конец
воспроизведения у самого конца — конец видео (`view_finish`), раньше, как и
истёкшие три минуты, — закрытая страница: остаток уходит beacon’ом.
Ошибки не повторяются, в лог пишется первая за просмотр. Значения, которых
у сервиса нет, — как у ТВ из User-Agent: экран 1920×1080, `4g`, без
блокировщика рекламы.

Подписанные ссылки на медиа запрашиваются с User-Agent ресивера Chromecast,
потому что CDN проверяет тот же User-Agent при загрузке HLS-сегментов. Для
другой прошивки ресивера его можно заменить через `MOVIE_PROVIDER_USER_AGENT`.

## Постеры

Постеры на сайте провайдера закрыты той же антибот-проверкой, поэтому сервис
отдаёт их через свою сессию:

```sh
curl --get --data-urlencode 'url=<posterLink>' \
  'http://localhost:8080/v1/posters' -o poster.jpg
```

Из ссылки берутся только путь и query: картинка всегда запрашивается с
текущего хоста провайдера. Провайдер меняет поддомены, поэтому сохранённые
ссылки со старым хостом продолжают работать, а другие хосты через сервис
недоступны. Ссылка без схемы `http`/`https` или без пути отклоняется (`400`);
ошибки источника возвращают `502`.

## CORS

HTTP-шлюз принимает запросы с любого источника
(`Access-Control-Allow-Origin: *`, методы `GET` и `DELETE`) и обрабатывает
preflight-запросы CORS.
