# Title API

Сборка и запуск:

```sh
make
./title-api
```

По умолчанию gRPC-сервер слушает `:50051`, а HTTP/JSON-шлюз — `:8080`.
Настройки:

- `GRPC_ADDR` — адрес gRPC-сервера;
- `HTTP_ADDR` — адрес HTTP-шлюза;
- `MOVIE_PROVIDER_BASE_URL` — базовый URL провайдера (если не задан,
  используется встроенный);
- `MOVIE_PROVIDER_USER_AGENT` — User-Agent ресивера (см. ниже);
- `TITLE_API_PUBLIC_URL` — публичный HTTP-адрес сервиса, используемый в
  ссылках на синтетические HLS master-плейлисты (по умолчанию
  `http://localhost:50052`);
- `TITLE_API_STATE_DB` — путь к SQLite-базе состояния (по умолчанию
  `title-api-state.db` в текущем каталоге);
- `HTTPS_PROXY` / `HTTP_PROXY` — прокси для исходящих запросов, в том числе
  `socks5://…`;
- `TZ` — часовой пояс браузера, которым сервис представляется
  дополнительному плееру (IANA, например `Europe/Samara`; по умолчанию
  `Europe/Moscow`): он должен совпадать с местом домашнего IP.
- `FACES_URL` — адрес сервиса лиц (`faces/` в корне репозитория, например
  `http://127.0.0.1:50060`), с которым работает «Кто в кадре»; без него
  запросы `/v1/faces…` отвечают `503`;
- `TITLE_API_FACES` — каталог картинок пауз (по умолчанию `faces` рядом с
  базой состояния);
- `MUSIC_URL` — адрес музыкального сервиса (`music/` в корне репозитория,
  например `http://127.0.0.1:50061`), с которым работает «Музыка»; без него
  запросы `/v1/music…` отвечают `503`;
- `TITLE_API_MUSIC` — каталог аудио, которое ждёт вопроса к Shazam (по
  умолчанию `music` рядом с базой состояния).

Антибот-сессия создаётся до запуска gRPC-сервера, обновляется каждые пять
минут и сразу же, если запрос наткнулся на новую проверку. После редиректа
провайдера сервис запоминает фактический хост в SQLite и использует его при
следующем запуске; исходный `MOVIE_PROVIDER_BASE_URL` остаётся резервным.

## Docker

Образ для amd64 и arm64 собирается GitHub Actions при каждом изменении
`title-api/` в `master` и публикуется в GitHub Container Registry:

```sh
docker run -p 8080:8080 ghcr.io/stepan-tikunov/wrtcast/title-api
```

Чтобы актуальный хост переживал пересоздание контейнера, подключите volume:

```sh
docker run -p 8080:8080 \
  -e TITLE_API_STATE_DB=/var/lib/title-api/state.db \
  -v title-api-state:/var/lib/title-api \
  ghcr.io/stepan-tikunov/wrtcast/title-api
```

Теги: `latest` (последний `master`), `sha-<коммит>` и `<версия>` для тегов
`v*`. Собрать локально: `docker build -t title-api .`

[`compose.yaml`](compose.yaml) рассчитан на VPS, где сервис доступен только
через WireGuard: HTTP-шлюз слушает WireGuard-адрес сервера, gRPC — только
loopback, наружу ничего не публикуется. Исходящие запросы можно направить
через SOCKS5-прокси на домашнем роутере, чтобы провайдер и его CDN видели тот
же IP, с которого потом загружаются сегменты:

```sh
WG_ADDR=10.0.0.1 EGRESS_PROXY=socks5://10.0.0.2:1080 docker compose up -d
docker compose pull && docker compose up -d     # обновление
```

## Идентификаторы

`title_id` — первые восемь шестнадцатеричных символов SHA-1 от корневого
домена (eTLD+1) из `MOVIE_PROVIDER_BASE_URL`, за которыми идёт десятичный ID
тайтла на сайте. Ни смена поддомена в `MOVIE_PROVIDER_BASE_URL`, ни
автоматически найденный актуальный хост этот префикс не меняют, поэтому ранее
сохранённые ID остаются рабочими. Для провайдера по умолчанию и ID `42185`
получается:

```text
64aee42642185
```

## Поиск

Полнотекстовый поиск принимает запросы от трёх символов:

```sh
grpcurl -plaintext \
  -d '{"query":"Дюна"}' \
  localhost:50051 \
  title.v1.TitleService/SearchTitles
```

Тот же метод доступен через аннотацию `google.api.http`:

```sh
curl --get --data-urlencode 'query=Дюна' \
  'http://localhost:8080/v1/search'
```

Результаты содержат ID тайтла, название, год и абсолютный URL постера.
Возвращается до 30 результатов с первой страницы поиска провайдера.

## Подробности о тайтле

Полная информация о тайтле, включая достоверный тип (фильм или сериал) и
каталог сезонов и серий, доступна через `GetTitleDetails`:

```sh
curl 'http://localhost:8080/v1/titles/64aee42643222'

grpcurl -plaintext \
  -d '{"title_id":"64aee42643222"}' \
  localhost:50051 \
  title.v1.TitleService/GetTitleDetails
```

Для фильмов `durationSeconds` берётся из метаданных плеера, если они есть.
Если нет, сервис открывает подписанный master-плейлист HLS и суммирует
длительности `#EXTINF` выбранного медиаплейлиста. У сериалов длительность
указывается для каждой серии, а не для тайтла целиком. Серии сериала
запоминаются на 5 минут: чаще этого провайдер о них не спрашивается, как
бы часто ни открывали страницу, и одновременные запросы к нему идут одним.

Что нового у сериалов, для значков на главной странице роутера:

```sh
curl -X POST 'http://localhost:8080/v1/series/updates' \
  -d '{"titleIds":["64aee42643222"],"upcomingTitleIds":["67c18f3642185"]}'  # GetSeriesUpdates
```

- `titleIds` (до 30) — сериалы, у которых нужна последняя серия у
  провайдера (`lastSeason`, `lastEpisode`) и номера всех его серий по
  сезонам (`seasons`). Провайдера спрашивают по
  очереди, пока не пройдут 15 с; кто не успел, приходит без последней
  серии, а его серии догружаются и запоминаются к следующему запросу.
- `upcomingTitleIds` (до 30) — только то, что ждёт сериал на TMDB.
- У каждого — `status` и `nextEpisode` TMDB, если тайтл сопоставлен и его
  данные TMDB есть в кэше (см. ниже). Ради этого запроса TMDB не ждут:
  нет данных или они устарели — они обновляются в фоне.
- Фильмы (по сопоставлению с TMDB или по страницам провайдера) в ответ не
  попадают.

### TMDB

Сервис сопоставляет свои тайтлы с TMDB, по одному тайтлу на TMDB
(`internal/tmdb`), каждый тайтл — при первом `GetTitleDetails`. Найденный
тайтл приходит в ответах как `tmdb: {id, mediaType}` (страница
`themoviedb.org/<movie|tv>/<id>`). Первый `GetTitleDetails` до 2 с ждёт
поиска TMDB и, если тот решает тайтл, отдаёт его сразу; иначе тайтл
сопоставляется в фоне, и `WaitTmdbMatch` (`GET /v1/titles/{id}/tmdb`) ждёт
этого до 15 с: `{tmdb, pending}`, `pending` — ещё не сопоставлен.
Включается это ключом API TMDB или токеном доступа (v4):
`UpdateTmdbSettings` (`POST /v1/tmdb`, `{"apiKey":"…"}`). Ключ перед
сохранением проверяется запросом `/authentication`, хранится в базе
состояния и наружу не отдаётся: `GetTmdbSettings` (`GET /v1/tmdb`) говорит
только, задан ли он, его последние четыре символа и почему не удалось
последнее сопоставление.

- Поиск TMDB (`language=ru-RU`) ищет тайтл по оригинальному названию и по
  русскому, среди фильмов или сериалов, смотря по типу тайтла. Если
  ровно один результат совпадает по названию (буквы и цифры без учёта
  регистра, ё как е) и году, это он.
- Иначе — нет совпадений или их несколько — тайтл пока остаётся
  несопоставленным и пробуется снова при следующем открытии. Claude
  выключен (`askClaude` в `internal/tmdb/service.go`); включённый, решает
  Claude Sonnet 5.5 (ключ
  из «Своей разметки», включать разметку не нужно): по описанию тайтла с
  сайта и кандидатам поиска, со своим поиском по TMDB и поиском в
  интернете (до пяти запросов). Названный им тайтл проверяется запросом
  к TMDB. Claude может ответить, что такого тайтла на TMDB нет; это тоже
  запоминается. Сколько это стоило, сервис пишет в лог и в базу.
- Тайтлы сопоставляются по одному. Без ключа Claude тайтл, который поиск
  не решил, пробуется снова при следующем открытии; неудачный — ещё
  дважды, открытый через 30 минут и через 2 часа. Отказ API (ключ,
  баланс, лимит) не считается неудачей тайтла.
- TMDB и API Claude вызываются напрямую, мимо `HTTPS_PROXY`.

Что показать на странице тайтла, сервис отдаёт по ID тайтла на TMDB, есть
такой тайтл у провайдера или нет:

```sh
curl 'http://localhost:8080/v1/tmdb/movie/693134'          # GetTmdbDetails
curl 'http://localhost:8080/v1/tmdb/tv/1405/seasons/1'     # GetTmdbSeason
curl 'http://localhost:8080/v1/tmdb/person/819'            # GetTmdbPerson
curl 'http://localhost:8080/v1/tmdb/images/w780/eZ239CUp1d6OryZEBPnO2n87gMG.jpg' -o backdrop.jpg
```

- `GetTmdbDetails` (`movie` или `tv`: у фильма и сериала ID бывает
  один): по-русски название, год, слоган, описание, жанры, страны,
  возраст по российской шкале (американский рейтинг переводится, если
  российского нет), фон без надписей (от 1280 px, лучший по голосам),
  логотип PNG (русский, английский, без языка) с отношением сторон,
  первые 12 актёров по титрам (с фото или без) и сколько их всего, до 4 трейлеров с YouTube (русские и официальные
  первыми), коллекция по порядку выхода, до 12 рекомендаций; у сериала —
  статус, последняя и следующая серии, сезоны, создатели. У людей
  (актёров, режиссёров, создателей) есть `id` для `GetTmdbPerson`. `title_id` —
  наш тайтл, если он сопоставлен, у самого тайтла, частей коллекции и
  рекомендаций. Нет на TMDB — `NOT_FOUND`, нет ключа —
  `FAILED_PRECONDITION`.
- `GetTmdbCast` (`GET /v1/tmdb/{movie|tv}/{id}/cast`): весь состав по
  титрам, до 300 человек, из того же кэша.
- `GetTmdbPerson` (`GET /v1/tmdb/person/{id}`): имя по-русски (если у
  TMDB оно латиницей — из переводов или `also_known_as`) и по-английски,
  фото, кем известен, даты и место рождения (по-русски из Wikidata: город
  и страна, иначе как у TMDB), биография (английская, если русской нет; без
  разметки Markdown, эмодзи и списков фильмов и наград в конце), ссылки на
  TMDB, Кинопоиск, IMDb, Википедию (русскую, иначе английскую) и Instagram —
  Кинопоиск и Википедия из Wikidata. Работы — до
  300 тайтлов, самые известные (по голосам) первыми, каждый один раз: роль,
  должности (режиссёр, сценарий, продюсер, музыка и т.п.), число серий,
  `title_id`, если сопоставлен. Ток-шоу, новости, реалити и роли «самого
  себя» пропускаются. Хранится 30 дней, сутки — если Wikidata не ответила.
- `GetTmdbSeason`: серии с кадром, описанием (английским, если русского
  нет), датой и длительностью; название пустое, если это только номер
  («Серия 5») или не по-русски; будущие серии — `upcoming`. Сезона нет
  на TMDB — пустой ответ.
- Выбранное хранится в базе состояния (`tmdb_cache`): сутки — у идущего
  сериала, тайтла не старше года и сезона с будущими сериями, 30 дней —
  у остального. Устаревшее отдаётся сразу и обновляется в фоне; если TMDB
  не ответил, остаётся старое.
- Картинки — имена файлов, их отдаёт `/v1/tmdb/images/{size}/{file}`
  (`w185`, `w300`, `w342`, `w500`, `w780`, `w1280`) с
  `image.tmdb.org`, с `Cache-Control: immutable`. Скачанные хранятся рядом
  с базой состояния (`tmdb-images`, или `TITLE_API_IMAGES`) до 500 МБ;
  давно не запрошенные удаляются при запуске и раз в час.

Тайтл TMDB, которого у нас нет (часть коллекции, рекомендация), ищется у
провайдера по запросу:

```sh
curl -X POST 'http://localhost:8080/v1/tmdb/movie/693134/lookup'  # LookupTmdbTitle
```

- Ответ — `{state, titleId}`, `state` — `STATE_FOUND` (`titleId` —
  наш тайтл), `STATE_NOT_FOUND` или `STATE_PENDING` (ещё ищется, спросить
  снова). Запрос ждёт до 15 с. Уже сопоставленный тайтл находится сразу.
- Иначе поиск идёт в фоне, по одному тайтлу: поиск провайдера по русскому
  названию и по оригинальному, оба сразу; из найденного — не больше трёх
  тайтлов того же года ±1 (сначала с тем же названием). Они открываются и
  сопоставляются с TMDB по названию и году все сразу; найден первый,
  сопоставившийся с этим тайтлом TMDB, если более вероятные уже не
  подошли. Тех, кого поиск TMDB не решил, затем по одному, начиная с
  вероятных, решает Claude (если он включён), пока один не сопоставится.
  Сопоставления открытых так тайтлов сохраняются как обычные.
- Не найденный тайтл ищется снова не раньше чем через неделю, неудачный
  поиск (провайдер не ответил) — через 30 минут (`tmdb_lookups`). К
  провайдеру поиск обращается только по такому запросу.

## Потоки

`GetPlaybackStreams` возвращает потоки фильма, если передан только `title_id`.
Для сериала передайте `season_number` и `episode_number`, чтобы выбрать серию:

```sh
curl 'http://localhost:8080/v1/titles/64aee42642185/playback-streams'

curl --get \
  --data-urlencode 'season_number=1' \
  --data-urlencode 'episode_number=1' \
  'http://localhost:8080/v1/titles/64aee42654016/playback-streams'

grpcurl -plaintext \
  -d '{"title_id":"64aee42654016","season_number":1,"episode_number":"1"}' \
  localhost:50051 \
  title.v1.TitleService/GetPlaybackStreams
```

Для фильмов поля сезона и серии игнорируются.

Ответ содержит по одной записи на каждый доступный плеер. В каждой записи —
человекочитаемое имя, подписанный URL master-плейлиста HLS, список
аудиодорожек без дублей и
доступные субтитры. Видеоварианты намеренно не перечисляются: HLS-плеер
выбирает их сам из master-плейлиста.

### Повтор, заставка и титры

Основной плеер размечает у серий (и у фильмов) части, которые можно
пропустить: `repeat` — повтор прошлых серий, `screen` — заставку, `titer` —
титры, с началом и концом в секундах и флагом `skip` (у титров со сценой
после них он `false`). Сервис отдаёт их как `sections`
(`[{kind,startSeconds,endSeconds,skippable}]`, `kind` — `KIND_RECAP`,
`KIND_INTRO` или `KIND_CREDITS`):

- в `GetTitleDetails` — у каждой серии, а у фильма — на верхнем уровне;
  размечены они на видео длительностью `durationSeconds` серии или фильма;
- в `GetPlaybackStreams` — у каждого потока, вместе с
  `sectionsDurationSeconds`, длительностью видео, на котором их разметили.
  Это метаданные серии или фильма, а не плеера: потоки дополнительного
  плеера (и основного, если разметил только один из них) получают разметку
  первого основного плеера, у которого она есть. Видео другого источника
  может быть немного длиннее или короче (логотип студии, обрезанный хвост),
  поэтому клиент сравнивает с этой длительностью свою.

Если разметки нет (у дополнительного плеера её не бывает), `sections` пуст.

#### Своя разметка

Серии, которые основной плеер не разметил, сервис может разметить сам
через API Claude (`internal/marking`, `internal/marker`). Включается это
`UpdateMarkingSettings` (`POST /v1/marking`, `{"enabled":true,"apiKey":"sk-ant-…"}`).
Ключ перед сохранением проверяется запросом списка моделей, хранится в базе
состояния и наружу не отдаётся: `GetMarkingSettings` (`GET /v1/marking`)
говорит только, задан ли он, его последние четыре символа и почему не
удалась последняя разметка.

- Размечаются только сериалы, впервые запущенные после появления этой
  возможности: клиент передаёт `first_play=true` в `GetPlaybackStreams`,
  когда тайтл запускают впервые, и сервис запоминает тайтл.
- Сериал, который зритель сохранил, клиент передаёт в `MarkEpisode`
  (`POST /v1/titles/<id>/marking`, `{"seasonNumber":1,"episodeNumber":"1"}`)
  с серией, с которой его начнут смотреть: сервис запоминает тайтл, как при
  `first_play`, и, пока разметка включена, ставит в очередь только эту
  серию, если основной плеер её не разметил.
- Запрос потоков серии такого сериала ставит в очередь её и две следующие,
  если у них нет разметки основного плеера и своей ещё нет. Очередь одна:
  серия за серией, сегменты по одному, с паузой 0,5 с.
- Разметка серии: по субтитрам (английским, иначе русским, иначе любым
  полным) Claude Haiku 5.5 находит части приблизительно; затем по кадрам
  самого лёгкого варианта (384 px, через 2 с) Claude Sonnet 5.5 размечает
  начало серии, а Haiku — конец, и наконец Haiku уточняет каждую границу по
  кадрам через 1/8 с. Серия обходится примерно в $0,03–0,04.
- Готовая разметка отдаётся как `sections` основного плеера, на видео
  длительностью `sectionsDurationSeconds`, и так же переходит на
  дополнительный плеер. Серия без субтитров не размечается; неудачная
  пробуется ещё дважды, через 30 минут и через 2 часа. Отказ API (ключ,
  баланс, лимит) не считается неудачей серии.
- API Claude вызывается напрямую, мимо `HTTPS_PROXY`.

Каждый запрос к Claude — сопоставления с TMDB и разметки — пишется в
таблицу `llm_requests` базы состояния (`internal/llmlog`): когда (`t`, unix),
зачем (`purpose`: `tmdb`, `marking head` и т. д.) и для чего (`subject`:
тайтл или серия), модель (ответившая, если запрос ушёл на другую), токены
(`input_tokens`, `output_tokens`, `cache_read`, `cache_write`), поиски в
интернете, стоимость в долларах, длительность (`ms`), чем кончился
(`stop`) или ошибка. Например:

```sh
sqlite3 title-api-state.db "SELECT datetime(t, 'unixepoch'), purpose, subject, model,
  input_tokens, output_tokens, round(cost, 4) FROM llm_requests ORDER BY t DESC LIMIT 20"
```

`cmd/sectionlab` — стенд, на котором подбиралась разметка: скачивает серию
(субтитры, начало и конец видео, эталонную разметку) и сравнивает с ней
разметку Claude.

#### Сверка с видео дополнительного плеера

Видео дополнительного плеера — другой энкод той же серии: оно может
начинаться на секунду-две раньше или позже, кончаться логотипом или идти с
другой частотой кадров. Поэтому разницу длительностей сервис не берёт на
веру, а сверяет оба видео по кадрам (`internal/provider/align.go`):

- Фрагменты, которые ресивер и так загружает через relay (и превью
  перемотки), сервис копирует себе. Как только набирается не меньше 8 с
  подряд, он декодирует их ffmpeg'ом в кадры 32×18 в градациях серого
  (без краёв, где логотипы дубляжа и чёрные полосы). Затем загружает то же
  место ±20 с у самого лёгкого варианта основного плеера (с домашнего
  адреса, как сам плеер) и ищет сдвиг, при котором кадры совпадают лучше
  всего. Совпадение принимается, если в среднем сходство ≥ 0,9 и на 0,05
  выше любого сдвига дальше 0,5 с: статичная сцена или титры на чёрном
  совпадают сами с собой при любом сдвиге и ничего не дают.
- Каждое совпадение — опорная точка (время основного видео и сдвиг в нём).
  Первая ищется сразу при старте просмотра, следующие — не ближе 10 минут
  к прежним (до трёх, в ±3 с от сдвига ближайшей), так что титры
  сдвигаются по точке рядом с ними, если энкоды расходятся. Между точками
  сдвиг интерполируется. Разную частоту кадров (24, 25, 23,976) сервис
  узнаёт по отношению длительностей.
- Точки хранятся по серии и дубляжу в базе состояния (`alignment:<ключ>`),
  повторный просмотр их не ищет.
- Энкоды одного релиза начинаются одинаково, поэтому сдвиг первой точки
  каждой серии запоминается и для сериала с этим дубляжом
  (`alignment:prior:<тайтл>|<дубляж>`, три последние серии). Серия, которую
  ещё не сверяли, сразу получает секции по сдвигу последней, если сдвиги
  этих серий расходятся не больше чем на секунду. Так посмотренная вчера
  серия n даёт таймкоды серии n+1 сразу при её запуске, а её собственные
  точки заменяют оценку, как только найдутся.
- Через 2 минуты после первой точки просмотра серии сервис сверяет
  заранее следующую серию того же дубляжа, если её точек ещё нет: получает
  её потоки, как для запуска (страница дополнительного плеера и подпись
  ссылок), и загружает у самого лёгкого качества master, медиаплейлист и
  2–3 фрагмента вокруг места, с которого начнётся просмотр (конец повтора и
  заставки, сдвинутый по сериалу; без них — 60 с). Сокет и просмотр при этом
  не открываются, ошибки в `/errors` плеера не уходят. Найденная точка
  хранится, как у любой серии, так что серия n+1 запускается с секциями и
  на следующий день. CDN уже блокировал домашний адрес, поэтому первый же
  его отказ выключает сверку заранее на 12 часов; если она не удалась,
  сервис хотя бы декодирует первые 45 с основного видео следующей серии.

Секции на видео дополнительного плеера приходят в ответе `headers` (см.
«Дополнительный плеер»). Без ffmpeg (`$FFMPEG` или `ffmpeg` в `PATH`; в
образе он есть) сверки нет, и клиент по-прежнему сравнивает длительности.

### Дополнительный плеер

Для страницы дополнительного плеера, его сайта, CDN и рекламной сети сервис —
один Chrome 152 на Windows: ClientHello Chrome (через
[tls-client](https://github.com/bogdanfinn/tls-client), с перемешиванием
расширений, как у Chrome), HTTP/2 там, где его даёт ALPN, с настройками,
окном и порядком псевдозаголовков Chrome, его User-Agent и `sec-ch-ua*`,
`Accept-Language: ru-RU,…`, и для каждого рода запроса страницы —
`Sec-Fetch-*`, `Accept`, `Priority`, `Origin` и `Referer`, как у Chrome, в
его порядке. Соединения общие для всех страниц, по одному HTTP/2 (или до
шести HTTP/1.1) на хост; WebSocket — своё соединение с ALPN `http/1.1` и
заголовками рукопожатия Chrome. Запросы hls.js к CDN несут свои заголовки,
поэтому перед каждым новым URL идёт CORS-preflight `OPTIONS`
(`access-control-request-headers: accepts-controls,authorizations`), с
кэшем на `Access-Control-Max-Age`. Cookie — только `SameSite=None`: плеер —
iframe чужого сайта. Основной плеер провайдера работает по-прежнему.

Страница загружается как iframe страницы провайдера: переход с её origin в
`Referer`, затем стили и скрипты страницы (из HTTP-кэша, пока свежи, потом с
`If-None-Match`/`If-Modified-Since`), спрайт иконок и проверка блокировщика
рекламы (HEAD на хост IMA, как в бандле). Запрос воспроизведения
(`/bnsi`) уходит, когда скрипты «выполнились» (0,25–0,9 с после их загрузки);
`av1=false`, как у ПК без аппаратного AV1. Отпечаток устройства хранится
вместе с «личностью» браузера (User-Agent без версий, пояс, экран, язык):
у прошлой личности, Chromecast, был другой.

Сервис возвращает каждый перевод отдельным `MediaStream`, а master со всеми
качествами собирает при первом запросе его URL. Как и плеер, грузящий одно
качество, он запрашивает master только того качества, с которого стартует
страница (последнее сыгранное, иначе 480, иначе 360); атрибуты остальных
выводятся из него, а ссылки вариантов ведут на сервис:
`GET /v1/media/<id>/quality/<качество>/playlist.m3u8` загружает master этого
качества (как смена качества в плеере) и его медиаплейлист, делает все URI
абсолютными и пять секунд отдаёт тот же ответ без нового запроса к CDN. Если
CDN отклонил ссылки (`403`, `X-VD: token_decrypt`), сервис
дважды заново запрашивает их у плеера (с вызовом из заголовка `Borth`
прошлого ответа, а если плеер его не принял, со свежей копией страницы), а
если не помогло, отдаёт `502`. Если CDN заблокировал самого клиента
(`X-VD: client_blocked` или `session_blocked`), повторов нет и master
отвечает `403`. Собранный master хранится в памяти шесть часов
(до 4096 последних). Когда ссылки истекают (`time` ответа), плеер, проверяя
раз в две минуты, запрашивает новые; сервис тоже, перезагружает сыгранные
качества и отправляет запросы старых сегментов на новые того же места. Имя перевода записывается в единственную
`audioTracks[].name`. Обязательные для внешнего медиапрокси HTTP-заголовки
возвращаются в `proxyHeaders` как список пар `name/value`. Его CDN ждёт на
каждом запросе, от master до сегментов, те же заголовки, что шлёт плеер:
`Origin` и `Referer` страницы плеера, отпечаток устройства в
`Accepts-Controls` и `Authorizations: Bearer <константа плеера>`. Отпечаток
создаётся один раз и хранится в базе состояния; тот же уходит в `Borth`
запроса воспроизведения, а к ссылкам субтитров, как и плеер, сервис
дописывает `?t=…&b=<отпечаток>`. Chromecast не может выставить такие
заголовки при прямой загрузке URL, поэтому эти потоки нужно передавать через
медиапрокси, который добавляет их и переписывает ссылки дочерних плейлистов и
сегментов, — или через сам сервис:
`GET /v1/media/<id>/cdn?u=<URL CDN>` загружает URL так, как его загрузила бы
страница плеера, и отдаёт статус, `Content-Type` и `X-VD` CDN, а тело —
потоком. Принимаются только хосты этого медиа (ссылки и плейлисты, которые
сервис уже видел, и субтитры), иначе `400`. После блокировки CDN
(`client_blocked`/`session_blocked`) relay десять минут сразу отвечает `403`,
не спрашивая CDN. Через relay сервис видит каждый фрагмент и считает по ним
оценку пропускной способности, как hls.js (EWMA с полупериодами 3 и 9 с).
Загрузки с `&pv=1` (превью кадров при перемотке в UI роутера) идут так же,
но в эту оценку, в то, докуда загружены фрагменты, и в ошибки плеера не
попадают: hls.js страницы их бы не загружал.

Если ответ плеера на запрос воспроизведения называет WebSocket (`pnr`,
`pnk`), сервис, как и плеер, держит его, пока источник играет: с первым
запросом master открывает сокет и шлёт `playback_start`, `resumed`, затем
`playing` каждые 30 секунд, `paused` на паузе (сердцебиение до `resumed`
молчит) и `seeked` после перемотки. При переподключении — снова
`playback_start`, а сердцебиение, как у плеера, молчит до следующего
`resumed`. Обрыв, переподключение и отказ после 30 попыток сокет, как плеер,
сообщает в `/stats` сайта плеера. Сервер отвечает `config_update` с
`edge_hash`, и он заменяет отпечаток в `Accepts-Controls`. Поэтому
медиапрокси берёт заголовки не из `proxyHeaders`, а у сервиса:

```sh
curl 'http://localhost:8080/v1/media/<id>/headers?q=720&t=125&p=0&w=0&d=2640&b=48000000&e=9000000'
# {"headers":[{"name":"Origin","value":"…"},…],"ttl":20,"proxy":"/v1/media/<id>/cdn",
#  "sections":[{"kind":"KIND_INTRO","startSeconds":94.3,"endSeconds":206.1,"skippable":true},…]}
```

`proxy` — путь relay; роутер, который его видит, загружает CDN через него.
`sections` — повтор, заставка и титры уже на видео этого источника, когда
оно сверено с видео основного плеера (см. «Сверка с видео дополнительного
плеера»); пока сверка в первые 20 с просмотра ещё идёт, вместо них
`"aligning":true`, а `ttl` — 2 с. Нет ни того, ни другого — сверки нет, и
секции считаются по длительностям.
`q` — играемое качество (цифры метки), `t` — позиция в секундах, `p` — `1`
на паузе, `w` — `1`, пока ТВ ждёт данных (BUFFERING), `d` — длительность, которую сообщил ТВ, `b` — байты сегментов этого
`id`, загруженные с начала воспроизведения, `e` — скорость их загрузки в
бит/с; все необязательны, смена `q` отправляет `playback_start`. Заголовки
можно держать `ttl` секунд: 20, пока идёт просмотр (см. ниже), 5, пока не
пришёл первый `edge_hash`. Каждый запрос продлевает сокет и просмотр; без
запросов три минуты они закрываются, а следующий запрос открывает их снова.
Ещё не собранный master при этом собирается, как при запросе master;
неизвестный `id` — `404`. Для источников без сокета ответ — те же постоянные
заголовки. Конец воспроизведения — `DELETE /v1/media/<id>/session` (`204`;
для клиентов, умеющих только GET и POST, — `POST
/v1/media/<id>/session/end`): сокет получает `ended` и закрывается.

Кроме сокета плеер сообщает о каждом просмотре сайту, с которого загружен
(те же cookie, `Origin` и `Referer` страницы, тот же прокси), и сервис делает
это за роутер — для каждого файла страницы, общим для его переводов (для
плеера это смена озвучки). `POST /stat` (форма jQuery) регистрирует просмотр
при первом запуске и повторяется, когда позиция, округлённая до процента,
равна 0, 10, 30, 60 или 97. `POST /events` (форма с JSON) получает события
плеера пачкой раз в 30 секунд от его старта, сразу после первого кадра и
перед сменой качества или озвучки: преролл, `view_start`, `startup`,
`play`, `playback_ready`, `first_frame`, `file_load_complete`,
`heartbeat` каждые 10 секунд, пока идёт воспроизведение (с позицией,
между запросами роутера досчитанной; `bytesLoadedTotal` в Chrome — 0: hls.js
отдаёт фрагмент своему worker’у раньше, чем бандл его считает), паузы,
перемотки, `rebuffer_start`/`rebuffer_end` (по `w`), смены, `view_percent`
и конец. Ошибки загрузок CDN, как ошибки hls.js, уходят в `POST /errors`:
`4xx` — фатальные и сразу, остальные — пачкой раз в 30 секунд.
Рекламу плеер берёт из списков рекламной сети (`lists.php`): преролл — по
«плей», фоновый слот — когда пошло видео, мидролл — на 300-й секунде;
сервис запрашивает списки в те же моменты с теми же полями, но любой
список считает пустым: VAST, креативы, показы и пиксели не запрашиваются.
Преролл длится, пока идут его запросы (при пустом ответе — второй). Первый запрос заголовков —
нажатие «плей», первый с длительностью — первый кадр. Конец
воспроизведения у самого конца — конец видео (`view_finish`), раньше, как и
истёкшие три минуты, — закрытая страница: остаток уходит beacon’ом.
Ошибки не повторяются, в лог пишется первая за просмотр. Значения, которых
у сервиса нет, — как у того же Chrome: экран 1920×1080, iframe 854×480,
`Win32`, `4g`, без блокировщика рекламы.

Подписанные ссылки основного плеера запрашиваются с User-Agent ресивера
Chromecast, потому что CDN проверяет тот же User-Agent при загрузке
HLS-сегментов. Для другой прошивки ресивера его можно заменить через
`MOVIE_PROVIDER_USER_AGENT`.

## Кто в кадре

На паузе роутер присылает сегмент, на котором стоит ТВ, и сервис говорит,
кто из актёров в кадре (`internal/faces`):

1. ffmpeg вырезает из сегмента кадр паузы в полном размере; кадр
   сохраняется и отдаётся сразу, остальное идёт в фоне.
2. Сервис лиц (`faces/`, InsightFace: SCRFD-2.5G и ArcFace R50 на CPU)
   находит лица и считает вектор каждого из пяти самых крупных от 40 px.
3. Каждое лицо сравнивается с эталонами людей серии: первые 20 по титрам
   сериала (у фильма — его состава) и до 10 гостей серии
   (`guest_stars` TMDB). Сходство с человеком — косинус векторов, среднее
   двух лучших эталонов одного источника с весом источника. Лица и люди
   назначаются парами, от самой похожей, каждый человек — одному лицу.
   «Точно» — от 0,40 и на 0,06 больше, чем у следующего, и только у
   лица от 64 px, не сильно повёрнутого; «похоже» — от 0,28, тогда
   приходят два самых похожих.
4. Кадр, лица, их векторы и кем их сочли хранятся (`face_pauses`,
   `face_sightings`, картинки в `TITLE_API_FACES`): для будущих кластеров
   лиц сериала и калибровки порогов.

Эталоны — векторы лиц с фото людей на TMDB (`face_refs`): до трёх
портретов (`/person/{id}/images`, по голосам; на портрете берётся самое
крупное лицо, если другого почти такого же нет) и до трёх кадров, где
человек отмечен (`tagged_images`: сперва кадры и фоны, потом постеры; из
нескольких лиц берётся похожее на его портреты от 0,35 и на 0,08 больше
следующего, без портретов — только единственное). Они готовятся в фоне по
одному человеку (~1 с на картинку на сервере), когда начинается серия
(`/v1/faces/prepare`) или на первой паузе; паузы идут вперёд них. Кто уже
готов, хранится в `face_prepared`; без единой картинки человека
пробуют снова через неделю.

```sh
curl --data-binary @segment 'http://localhost:8080/v1/faces?title_id=<id>&season=1&episode=3&t=182&offset=2'
# {"pause":1,"frame":"/v1/faces/frames/1.jpg","width":1280,"height":720,
#  "faces":[],"preparing":true,"finding":true}
curl http://localhost:8080/v1/faces/pauses/1
# {"pause":1,"frame":"/v1/faces/frames/1.jpg","width":1280,"height":720,
#  "faces":[{"box":[546,57.3,855.8,443.1],"crop":"/v1/faces/crops/1.jpg",
#    "person":{"id":3787911,"name":"Brayden Gleave","character":"Jimmy Powell",
#      "profile":"j6ro….jpg","portrait":"/v1/faces/crops/1.jpg"},
#    "score":0.569,"sure":true}],"preparing":false,"finding":false}
```

- `POST /v1/faces?title_id=&season=&episode=&t=&offset=` — тело: сегмент,
  как его отдал CDN (у fMP4 сперва init-сегмент); `offset` — секунды паузы
  от начала сегмента, `t` — от начала видео. Отвечает, как только кадр
  вырезан: `faces` пустые, `finding` — лица ещё ищутся, их отдаёт
  `GET /v1/faces/pauses/{id}`. `box` — в пикселях `frame`
  (длинная сторона до 1280), `crop` — лицо из кадра 256×256, `portrait` —
  лучшее лицо этого человека из пауз этого тайтла, которое было «точно».
  `preparing` — эталоны части людей ещё готовятся: позже паузу стоит
  спросить снова. `409` — тайтл не сопоставлен с TMDB, `422` — в сегменте
  нет такого кадра.
- `GET /v1/faces/pauses/{id}` — лица паузы, по эталонам на сейчас. Пока
  они ищутся, ждёт их до 15 с; не дождался — `finding`, без лиц.
- `POST /v1/faces/prepare?title_id=&season=&episode=` — готовит эталоны
  людей серии заранее: `{"preparing":true}`, если кого-то ещё нет.
- `GET /v1/faces/frames/{id}.jpg`, `/v1/faces/crops/{id}.jpg` — кадр паузы и
  лицо (не меняются); хранятся последние 300 кадров и лица до 300 МБ,
  портреты не удаляются.
- `GET /v1/faces/portraits/{tv|movie}:{tmdb_id}/{person}` — портрет
  человека из пауз тайтла (может смениться лучшим).

## Музыка

Что играет в фильме или серии. Роутер присылает аудио каждого сегмента,
который получает: и тех, что смотрит ТВ, и тех, что качает вперёд. Каждые
полсекунды музыкальный сервис (`MUSIC_URL`, YAMNet) оценивает, насколько это
музыка, речь и песня.

Отрезок музыки — от 8 с подряд: музыка от 0,5, и при этом речь до 0,3 или
песня от 0,3. Разрывы внутри отрезка — до 2,5 с. Фоновый саундтрек под
диалогом Shazam почти не узнаёт, а песни узнаёт и под диалогом.

О каждом отрезке Shazam спрашивают один раз в фоне, по 8 самым «музыкальным»
секундам. Если отрезок от 30 с и первый вопрос ничего не дал, спрашивают ещё
раз, не ближе 20 с от первого места. Если Shazam назвал трек и его длину,
следующий отрезок в пределах этой длины, начавшийся не позже чем через
минуту после его музыки, считается тем же треком и Shazam о нём не
спрашивают: это песня, которую перебил диалог.

Вопросы идут по одному: сначала о видео, которое смотрели последним, среди
видео за последние 6 часов. Частоту задаёт сервис: 8 вопросов за 5 минут.
Узнанное хранится всегда, поэтому при повторном просмотре видно сразу.
Аудио с музыкой хранится сутки (не больше 1 ГБ), без музыки не хранится.

```sh
curl -X POST --data-binary @segment.aac \
  'http://localhost:8080/v1/music/audio?title_id=<id>&season=1&episode=2&source=alternative&start=1304&stop=1308'
# {"ok":true}
curl 'http://localhost:8080/v1/music?title_id=<id>&season=1&episode=2&source=alternative'
# {"tracks":[{"start":0,"stop":24,"offset":94.8,"key":"109354078",
#   "title":"Don't Stop Believin'","artist":"Journey","cover":"https://…/400x400cc.jpg",
#   "url":"https://www.shazam.com/track/…","apple_url":"https://music.apple.com/…",
#   "spotify":"spotify:search:…","duration":248.9}],"pending":0,"received":24}
```

- `POST /v1/music/audio` — аудио одного сегмента (ADTS AAC, как его вырезает
  роутер, до 4 МБ). `start`/`stop` — секунды на видео этого источника
  (`source` — плеер: у разных плееров разное время). Где в нём музыка,
  известно сразу после ответа; повторно присланное не разбирается.
- `GET /v1/music` — узнанные к этому моменту треки по порядку:
  - `start`–`stop` — где трек звучит на видео;
  - `offset` — секунда трека в `start`;
  - `pending` — сколько вопросов к Shazam ещё предстоит;
  - `received` — сколько секунд аудио получено.

## Постеры

Постеры на сайте провайдера закрыты той же антибот-проверкой, поэтому сервис
отдаёт их через свою сессию:

```sh
curl --get --data-urlencode 'url=<posterLink>' \
  'http://localhost:8080/v1/posters' -o poster.jpg
```

Из ссылки берутся только путь и query: картинка всегда запрашивается с
текущего хоста провайдера. Провайдер меняет поддомены, поэтому сохранённые
ссылки со старым хостом продолжают работать, а другие хосты через сервис
недоступны. Ссылка без схемы `http`/`https` или без пути отклоняется (`400`);
ошибки источника возвращают `502`.

## CORS

HTTP-шлюз принимает запросы с любого источника
(`Access-Control-Allow-Origin: *`, методы `GET` и `DELETE`) и обрабатывает
preflight-запросы CORS.
